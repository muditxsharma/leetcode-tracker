## Problem (summary)

Table: Transactions

+---------------+---------+
| Column Name   | Type    |
+---------------+---------+
| id            | int     |
| country       | varchar |
| state         | enum    |
| amount        | int     |
| trans_date    | date    |
+---------------+---------+
id is the primary key of this table.
The table has information about incoming transactions.
The state column is an enum of type ["approved", "declined"].

 

Write an SQL query to find for each month and country, the number of transactions and their total amount, the number of approved transactions and their total amount.

Return the result table in any order.

The query result format is in the following example.

 

Example 1:

Input: 
Transactions table:
+------+---------+----------+--------+------------+
| id   | country | state    | amount | trans_date |
+------+---------+----------+--------+------------+
| 121  | US      | approved | 1000   | 2018-12-18 |
| 122  | US      | declined | 2000   | 2018-12-19 |
| 123  | US      | approved | 2000   | 2019-01-01 |
| 124  | DE      | approved | 2000   | 2019-01-07 |
+------+---------+----------+--------+------------+
Output: 
+----------+---------+-------------+-----

(Truncated.)

## Approach

**Approach**

1. **Extract the month** from `trans_date` using `DATE_FORMAT(trans_date, '%Y-%m')`. This gives a string like `2023-07` which is used as the first grouping key.
2. **Group** the rows by the derived month and the `country` column.
3. **Aggregate** the required metrics in a single pass:
   * `COUNT(id)` → total number of transactions (`trans_count`).
   * `SUM(CASE WHEN state='approved' THEN 1 ELSE 0 END)` → number of approved transactions (`approved_count`).
   * `SUM(amount)` → total amount of all transactions (`trans_total_amount`).
   * `SUM(CASE WHEN state='approved' THEN amount ELSE 0 END)` → total amount of approved transactions (`approved_total_amount`).
4. Return the columns in the order required by the problem. No additional sub‑queries or CTEs are needed – everything is done with **conditional aggregation**.

```sql
SELECT DATE_FORMAT(trans_date, '%Y-%m') AS month,
       country,
       COUNT(id)                                            AS trans_count,
       SUM(CASE WHEN state = 'approved' THEN 1 ELSE 0 END) AS approved_count,
       SUM(amount)                                          AS trans_total_amount,
       SUM(CASE WHEN state = 'approved' THEN amount ELSE 0 END) AS approved_total_amount
FROM   Transactions
GROUP BY DATE_FORMAT(trans_date, '%Y-%m'), country;
```

---

**Why it works**
- The `GROUP BY` creates a distinct bucket for each `(month, country)` pair.
- The `CASE` expressions turn the boolean condition `state='approved'` into numeric values, allowing `SUM` to count or total only the approved rows while leaving declined rows contributing `0`.
- All required statistics are computed in a single scan of the table, which is optimal for this type of reporting query.

## Complexity

- **Time:** O(N) – the query scans each row once (grouping and aggregation are linear in the number of input rows).
- **Space:** O(G) – additional space proportional to the number of distinct (month, country) groups generated by the GROUP BY clause.

## Pros

- Single‑pass computation – no sub‑queries or joins needed
- Uses conditional aggregation, which is concise and easy to read
- Works for any number of countries and months without schema changes

## Cons

- `DATE_FORMAT` on `trans_date` prevents the use of a plain index on `trans_date` (may cause a full table scan)
- If the `state` column contains values other than 'approved'/'declined', they are silently ignored in the approved aggregates
- Result order is unspecified; an ORDER BY clause would be needed for deterministic ordering

## Edge cases

- Months that contain only declined transactions – `approved_count` and `approved_total_amount` correctly appear as 0
- Countries with no transactions for a given month are omitted from the result (as expected)
- `trans_date` values on the first/last day of a month are handled correctly because the month string is derived from the full date
- If `amount` can be NULL, the `SUM(amount)` will ignore NULLs; ensure data guarantees non‑NULL amounts or coalesce to 0
